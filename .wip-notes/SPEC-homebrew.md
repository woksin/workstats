## 1. What the workflow's Homebrew job actually does

File: `/Volumes/sourcecode/repos/woksin/workstats/.github/workflows/release.yml`, lines 217–329.

### Job header and inputs (lines 217–231)

```yaml
  homebrew:
    name: Update the Homebrew tap
    if: needs.release.outputs.publish == 'true'
    needs: [release, attach]
    runs-on: ubuntu-latest

    # A deploy key rather than a personal access token: it grants write to the
    # tap repository and to nothing else, so the worst a leak can do is publish
    # a bad formula. A PAT would carry every repository the account can reach.
    env:
      TAP_KEY: ${{ secrets.HOMEBREW_TAP_DEPLOY_KEY }}
      TAP_REPO: woksin/homebrew-workstats
      VERSION: ${{ needs.release.outputs.version }}
      TAG: ${{ needs.release.outputs.tag }}
```

- Secret name is **`HOMEBREW_TAP_DEPLOY_KEY`**, an **Actions** secret on **`woksin/workstats`**.
- Tap repository is hardcoded to **`woksin/homebrew-workstats`**.
- For the current release, `VERSION = 1.0.2` and `TAG = v1.0.2`.

### The guard that hides the failure (lines 236–244)

```yaml
      - name: Is the tap configured?
        id: guard
        run: |
          if [ -z "${TAP_KEY:-}" ]; then
            echo "No HOMEBREW_TAP_DEPLOY_KEY secret — skipping the tap." >> "$GITHUB_STEP_SUMMARY"
            echo "configured=false" >> "$GITHUB_OUTPUT"
          else
            echo "configured=true" >> "$GITHUB_OUTPUT"
          fi
```

Every subsequent step carries `if: steps.guard.outputs.configured == 'true'`. With no secret the job
runs one `echo`, skips three steps, and exits green. The only trace is a line in the run's step
summary — no annotation, no warning, nothing that surfaces in a PR check or the Actions list view.
**This is the mechanism that hid the broken README for every release.**

### Formula generation (lines 253–300)

```yaml
      - name: Write the formula
        if: steps.guard.outputs.configured == 'true'
        run: |
          set -euo pipefail
          sha() { shasum -a 256 "./artifacts/workstats-$1.tar.gz" | cut -d' ' -f1; }
          base="https://github.com/woksin/workstats/releases/download/${TAG}"

          mkdir -p out
          cat > out/workstats.rb <<RUBY
          # Generated by the release workflow in woksin/workstats. Do not edit by hand.
          class Workstats < Formula
            ...
            on_macos do
              on_arm do
                url "${base}/workstats-macos-arm64.tar.gz"
                sha256 "$(sha macos-arm64)"
```

The SHA256 source is the **build artifacts of the same run** (`./artifacts/...`), downloaded by the
preceding step:

```yaml
      - name: Download artifacts
        if: steps.guard.outputs.configured == 'true'
        uses: actions/download-artifact@v8
        with:
          path: ./artifacts
          merge-multiple: true
```

Not the release assets. They happen to be byte-identical (the `attach` job uploads the very same
files) — see §4 — but it is an indirection worth knowing about, and it is why the job cannot be run
standalone against an arbitrary tag.

### Push (lines 302–329)

```yaml
      - name: Push it to the tap
        if: steps.guard.outputs.configured == 'true'
        run: |
          set -euo pipefail
          mkdir -p ~/.ssh
          printf '%s\n' "$TAP_KEY" > ~/.ssh/tap_key
          chmod 600 ~/.ssh/tap_key
          ssh-keyscan -t ed25519 github.com >> ~/.ssh/known_hosts 2>/dev/null
          export GIT_SSH_COMMAND="ssh -i ~/.ssh/tap_key -o IdentitiesOnly=yes"

          git clone --depth 1 "git@github.com:${TAP_REPO}.git" tap
          mkdir -p tap/Formula
          cp out/workstats.rb tap/Formula/workstats.rb
          ...
          git add Formula/workstats.rb
          if git diff --cached --quiet; then
            echo "Formula already at ${VERSION}, nothing to push."
            exit 0
          fi
          git commit -m "workstats ${VERSION}"
          git push
```

Key facts this pins down:

| Question | Answer (verified from the above) |
|---|---|
| Auth mechanism | SSH deploy key over `git@github.com:` — **not** a PAT, **not** `GITHUB_TOKEN` |
| Key must be | An **ed25519** (or any OpenSSH) private key with **no passphrase** (nothing supplies one) |
| Key must live on | The **tap** repo `woksin/homebrew-workstats`, with **write** access |
| Secret must live on | The **source** repo `woksin/workstats`, named `HOMEBREW_TAP_DEPLOY_KEY` |
| Path written | `Formula/workstats.rb` (created with `mkdir -p` if absent) |
| Branch pushed to | Whatever the tap's **default branch** is — bare `git push`, no branch named |
| Repo must be | Non-bare, clonable by that key. It may be **empty**; see §2.4 |

## 2. What must exist for this to succeed

### 2.1 The tap repository

- **Name: `woksin/homebrew-workstats`** — mandatory, not a choice. Homebrew maps the tap reference
  `user/name` to the repository `user/homebrew-name`. Verified in
  `/opt/homebrew/Library/Homebrew/tap.rb:299`:
  ```ruby
  @full_repository = T.let("homebrew-#{@repository}", String)
  ```
  So `brew tap woksin/workstats` resolves to `https://github.com/woksin/homebrew-workstats`, which
  is exactly what `TAP_REPO` in the workflow points at. Consistent. (verified)

- **Visibility: public.** `brew tap` clones over anonymous HTTPS. A private tap would reproduce the
  exact error the user hit (`could not read Username for 'https://github.com'`). The source repo is
  already public, so there is nothing to protect. (verified reasoning; visibility requirement is
  standard Homebrew behaviour)

### 2.2 Directory layout — `Formula/`, confirmed for *this* workflow

Homebrew accepts three layouts. Verified in `/opt/homebrew/Library/Homebrew/tap.rb:968`:

```ruby
@potential_formula_dirs ||= T.let([path/"Formula", path/"HomebrewFormula", path].freeze, ...)
```

`Formula/` is first and is the conventional choice. **This workflow writes
`Formula/workstats.rb`** (line 313–314, `mkdir -p tap/Formula` then `cp out/workstats.rb
tap/Formula/workstats.rb`). So the required layout is:

```
woksin/homebrew-workstats
└── Formula/
    └── workstats.rb
```

Do **not** pre-create a root-level `workstats.rb`; the workflow would never touch it and Homebrew
would find two formulae or the wrong one.

### 2.3 Deploy key and secret

- One ed25519 keypair, no passphrase.
- **Public** half → deploy key on `woksin/homebrew-workstats`, **write enabled**.
- **Private** half → Actions secret `HOMEBREW_TAP_DEPLOY_KEY` on `woksin/workstats`.
- GitHub enforces that a deploy key is globally unique across the account: a key already registered
  as an account SSH key or as a deploy key elsewhere is rejected with "key is already in use".
  Generate a fresh, dedicated pair.

### 2.4 Does the tap repo need an initial commit?

**No — but create one anyway.** I tested this (verified, git 2.50.1 locally):

```
$ git clone --depth 1 file://…/empty.git tap
warning: You appear to have cloned an empty repository.
$ git config --get branch.main.remote   → origin
$ git config --get branch.main.merge    → refs/heads/main
$ git commit … && git push              → succeeds, exit 0
```

Cloning an empty repository still writes upstream tracking config for the unborn default branch, so
the workflow's bare `git push` works. Creating the repo with `--add-readme` is still preferable: it
gives the tap a landing page and makes the default branch unambiguous.

```bash

  --repo woksin/homebrew-workstats \
  --allow-write \
  --title "workstats release workflow"
```

`--allow-write` (`-w`) is mandatory — verified from `gh repo deploy-key add --help`. Without it the
`git push` fails with `ERROR: The key you are authenticating with has been marked as read only.`

Verify:

```bash
gh repo deploy-key list --repo woksin/homebrew-workstats
```

### Step 4 — add the private half as the secret on the **source** repo

```bash
gh secret set HOMEBREW_TAP_DEPLOY_KEY \
  --repo woksin/workstats \
  --app actions < ~/.ssh/workstats_tap_deploy
```

Reading from stdin preserves the key's newlines, which OpenSSH requires. Do **not** paste it through
`--body`; a key mangled onto one line produces `Load key: error in libcrypto` at clone time.

Verify:

```bash
gh secret list --repo woksin/workstats
```

Expect one row: `HOMEBREW_TAP_DEPLOY_KEY`.

```bash
GIT_SSH_COMMAND="ssh -i ~/.ssh/workstats_tap_deploy -o IdentitiesOnly=yes" \
```

Should list refs. If it prints `Permission denied (publickey)`, Step 3 went to the wrong repo.

## 4. Would the generated formula actually work? — verified, no mismatch

I reproduced the workflow's `Write the formula` step verbatim against the four real v1.0.2 release
tarballs. Results:

**Asset names match exactly.** The formula builds four URLs; all four exist on the release
(verified via `gh release view v1.0.2 --json assets`):

| Formula expects | On the v1.0.2 release | Match |
|---|---|---|
| `workstats-macos-arm64.tar.gz` | present, 3 281 822 B | ✅ |
| `workstats-macos-x86_64.tar.gz` | present, 3 524 427 B | ✅ |
| `workstats-linux-arm64.tar.gz` | present, 3 479 484 B | ✅ |
| `workstats-linux-x86_64.tar.gz` | present, 3 676 664 B | ✅ |

(`workstats-windows-x86.exe`, `workstats-windows-x86_64.exe` and `SHA256SUMS` are also on the
release; the formula correctly ignores them.)

**URL shape is correct and anonymously reachable.** `base` is
`https://github.com/woksin/workstats/releases/download/v1.0.2` — the tag, not the version. An
anonymous `curl -IL` on the arm64 URL returns **HTTP 200**. (verified)

**SHA256 source is sound.** The formula hashes the *build artifacts*, while users download the
*release assets*. These are the same bytes: the `attach` job uploads those very artifact files. I
confirmed the chain independently — downloading `workstats-macos-arm64.tar.gz` from the release and
hashing it locally gives `8ca28af789be4502882c8bf6d5358c06d5dc58f3d7ad42771616ab8c0fe51b56`, which
is both the value the reproduced generator emitted and the value in the release's `SHA256SUMS`.
All four match. (verified)

**Formula DSL is valid.** `ruby -c` passes. `on_macos` / `on_linux` / `on_arm` / `on_intel` are all
defined and freely nestable — verified in `/opt/homebrew/Library/Homebrew/on_system.rb`
(`ARCH_OPTIONS = [:intel, :arm]`, `BASE_OS_OPTIONS = [:macos, :linux]`, each turned into a plain
conditional block method by `setup_arch_methods` / `setup_base_os_methods`). A formula with no
top-level `url` but a declared `version` plus per-platform `url`/`sha256` is the standard shape for
binary-only formulae.

**Tarball layout matches `bin.install`.** `tar -tzf workstats-macos-arm64.tar.gz` lists exactly one
entry, `workstats`, at the root — matching `bin.install "workstats"` and the `Package` step's
`tar -czf … -C "$(dirname "$BUILT")" workstats`. (verified)

**No shell/Ruby interpolation collision.** The heredoc is unquoted (`<<RUBY`), so `${base}`,
`${VERSION}` and `$(sha …)` expand as intended. The Ruby body's only interpolation is
`"#{bin}/workstats --version"`, and `#{…}` is inert to the shell. No backticks, no stray `$`. Safe.
(verified by reproduction)

### ⚠️ The real silent-failure risk (found, reproduced)

**`sha()` failing does not fail the step. It emits `sha256 ""`.**

`set -euo pipefail` does *not* abort on a failing command substitution inside a heredoc body. I
reproduced this:

```
$ # artifacts/workstats-macos-arm64.tar.gz deliberately absent
shasum: ./artifacts/workstats-macos-arm64.tar.gz: No such file or directory
STEP EXIT AFTER HEREDOC: reached end
=== bash -c exit code: 0 ===
      url "https://example/v1.0.2/workstats-macos-arm64.tar.gz"
      sha256 ""
```

The step exits **0**, the formula is committed and pushed, the release is green — and every user on
that platform gets a checksum mismatch from `brew install`. This is the same failure shape as the
one just diagnosed, one layer deeper: **the workflow is structurally prone to reporting success
while producing garbage.** Trigger conditions include a renamed matrix leg, a partial
`download-artifact`, or a `merge-multiple` collision. Fix in §6.

### Secondary risk: `shasum` availability

`sha()` calls `shasum` unconditionally on `ubuntu-latest`. The `Package` step, by contrast, guards
it (`if command -v shasum >/dev/null; then … else sha256sum …`), which suggests the author was not
certain it is always present. `shasum` ships with the `perl` package and is present on GitHub's
`ubuntu-24.04` images, so this almost certainly works today — but combined with the bug above, a
missing `shasum` would silently produce a formula with **four** empty `sha256` values. **(low
likelihood, unverified on the runner; high blast radius)** Harden it in §6.

## 5. The `brew trust` requirement — the removed README text was accurate

The removed line read:

```bash
brew trust woksin/workstats   # Homebrew 6 gates third-party taps
```

**This is correct.** Verified against the locally installed Homebrew 6.0.18-12-gdf30fd3:

- `brew trust` exists: `brew help trust` → *"Trust non-official tap formulae, casks or commands so
  Homebrew may load them."* Trusted entries live in `~/.homebrew/trust.json` (or
  `$XDG_CONFIG_HOME/homebrew/trust.json`).
- Enforcement is **on by default**. `/opt/homebrew/Library/Homebrew/env_config.rb:659`:
  ```ruby
  HOMEBREW_REQUIRE_TAP_TRUST: {
    description: "If set, require non-official tap formulae, casks and commands to be trusted with "\
                 "`brew trust` before Homebrew loads them. This is the default unless "\
                 "`$HOMEBREW_NO_REQUIRE_TAP_TRUST` is set. …",
    disabled_by: :HOMEBREW_NO_REQUIRE_TAP_TRUST,
    default:     true,
  },
  ```
- The gate fires at **formula load**, not at `brew tap`. `brew tap woksin/workstats` succeeds
  regardless (`cmd/tap.rb` contains no trust logic). It is `brew install` that then fails.
- Two distinct failure messages, both verified in `trust.rb`:
  - short name (`brew install workstats`) — the tap is skipped during lookup:
    `opoo "Skipping #{tap.name} because it is not trusted. Run \`brew trust #{tap.name}\` to trust it."`
  - fully-qualified name — a hard error:
    `raise UntrustedTapError, "Refusing to load #{type} #{name} from untrusted tap #{tap.name}.\nRun \`brew trust --#{type} #{name}\` or \`brew trust #{tap.name}\` to trust it."`

### One correction worth making

**`brew trust` predates Homebrew 6.** It first shipped in **5.1.15** (commit `5fbcad25e9`,
"Add tap trust commands", 2026-05-30 — verified via `git tag --contains` in `/opt/homebrew`). Saying
"Homebrew 6" is close enough for a README but slightly overstates the floor.

### The better user-facing instruction

There is a **one-command** form that is strictly better than the three-line block. Verified in
`/opt/homebrew/Library/Homebrew/cmd/install.rb:195–204`:

```ruby
args.named.each do |name|
  if (tap_with_name = Tap.with_formula_name(name))
    tap, = tap_with_name
  …
  tap&.ensure_installed!
end
Homebrew::Trust.trust_fully_qualified_items!(args.named, type: args.only_formula_or_cask)
```

`ensure_installed!` auto-taps, then `trust_fully_qualified_items!` auto-trusts — but **only** when
the name is fully qualified (`trust.rb:118`: `next unless ::Utils.full_name?(name)`). So:

```bash
brew install woksin/workstats/workstats
```

taps, trusts, and installs in one command — and it grants **formula-level** trust
(`woksin/workstats/workstats`) rather than trusting the entire tap forever, which is the narrower
and better default. It also works unchanged on Homebrew 5.x, where trust does not exist. Subsequent
bare `brew upgrade` runs continue to work, because the formula-level trust entry persists.

`brew trust woksin/workstats` (whole-tap trust) remains the right instruction for anyone who wants
`brew install workstats` by short name to resolve.

## 6. Stopping the recurrence

The root cause is not the missing tap — it is that **a job can report success while doing nothing,
and nothing anywhere cross-checks the workflow's capabilities against what the README promises.**
Three changes, in priority order.

### 6.1 (Highest value) Make the guard loud, and tie it to what the README advertises

In `.github/workflows/release.yml`, replace the `Is the tap configured?` step (lines 236–244) with a
version that decides between *"intentionally not configured"* and *"advertised but broken"*, by
looking at the README itself:

```yaml
      - uses: actions/checkout@v7
        with: { sparse-checkout: README.md, sparse-checkout-cone-mode: false }

      - name: Is the tap configured?
        id: guard
        run: |
          set -euo pipefail
          advertised=false
          grep -qF 'woksin/workstats/workstats' README.md && advertised=true
          grep -qF 'brew tap woksin/workstats'  README.md && advertised=true

          if [ -n "${TAP_KEY:-}" ]; then
            echo "configured=true" >> "$GITHUB_OUTPUT"
          elif [ "$advertised" = true ]; then
            echo "::error title=Homebrew tap advertised but not configured::README documents a Homebrew install path, but HOMEBREW_TAP_DEPLOY_KEY is not set on this repository. Either configure the tap or remove the instructions from README.md."
            exit 1
          else
            echo "::warning title=Homebrew tap skipped::No HOMEBREW_TAP_DEPLOY_KEY secret; the tap was not updated."
            echo "No HOMEBREW_TAP_DEPLOY_KEY secret — skipping the tap." >> "$GITHUB_STEP_SUMMARY"
            echo "configured=false" >> "$GITHUB_OUTPUT"
          fi
```

Effect: the two states become distinguishable. A repo that has deliberately not set up a tap and
does not advertise one gets a **warning annotation** (visible in the run header and the Actions
list, unlike a step-summary line). A repo whose README promises `brew install` while the secret is
missing **fails the release** — which is precisely the signal that was absent for every release up
to v1.0.2.

Note this step needs a checkout; the `homebrew` job currently has none. A sparse checkout of just
`README.md` keeps it cheap.

### 6.2 Make an unhashable artifact fail the step instead of emitting `sha256 ""`

Still in `.github/workflows/release.yml`, in `Write the formula` (lines 253–300), hoist the hashing
out of the heredoc so `set -e` can see it, and assert the result:

```bash
set -euo pipefail
sha() {
  local f="./artifacts/workstats-$1.tar.gz" d
  [ -f "$f" ] || { echo "missing artifact: $f" >&2; exit 1; }
  if command -v sha256sum >/dev/null; then d=$(sha256sum "$f" | cut -d' ' -f1)
  else                                     d=$(shasum -a 256 "$f" | cut -d' ' -f1); fi
  [[ "$d" =~ ^[0-9a-f]{64}$ ]] || { echo "bad digest for $f: '$d'" >&2; exit 1; }
  printf '%s' "$d"
}
SHA_MACOS_ARM=$(sha macos-arm64)
SHA_MACOS_X86=$(sha macos-x86_64)
SHA_LINUX_ARM=$(sha linux-arm64)
SHA_LINUX_X86=$(sha linux-x86_64)
```

…then reference `${SHA_MACOS_ARM}` etc. in the heredoc instead of `$(sha macos-arm64)`. Assigning to
a variable at statement level *is* covered by `errexit`, unlike a substitution buried in a heredoc.
The `sha256sum`-first ordering also removes the `shasum`-availability question from §4.

Add a post-generation assertion before the push step:

```bash

[ "$(grep -c '^      sha256 "' out/workstats.rb)" -eq 4 ] || { echo "expected 4 sha256 lines" >&2; exit 1; }
```

```yaml
      - name: Verify the tap
```
